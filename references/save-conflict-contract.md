# 自动保存与编辑冲突

用于自动保存、并发编辑和乐观更新。复用项目已有的数据缓存与版本机制。

## 保存状态与草稿

- 通过当前草稿的修订标识判断「未保存／保存中／已保存／保存失败」。请求成功时，只有该响应对应的内容仍是当前草稿，才显示当前内容已保存。
- 保存期间用户继续编辑时，保留新草稿。旧响应只确认其提交的版本，不能清空或覆盖后续输入。
- 自动保存按业务选择串行合并或带版本的并发写入。乐观更新失败时，只回滚仍属于该次操作的变更，避免覆盖更晚的操作。

## 服务端版本与冲突

- 接口提供实体版本或强 ETag，保存时带上读取时的版本。服务端原子校验版本后更新，防止两个窗口相互覆盖。
- HTTP 条件写入可用 ETag 与 If-Match。前置条件不成立时返回 412。项目使用其他冲突码时，明确响应语义和最新版本获取方式。
- 冲突时保留用户草稿，获取权威的新版本，按产品能力提供比较、合并或重新应用。覆盖他人修改的操作需要明确意图，并继续通过服务端权限和版本规则执行。

下面是接口形态示例，路径与版本值由项目提供。

```http
PATCH /documents/example
If-Match: "v7"
Content-Type: application/json

{"title":"更新后的标题"}
```

## 响应丢失与重试

请求超时可能发生在写入已完成之后。先查询结果或按项目幂等机制确认原操作，避免重复创建记录。账号、实体 ID 与修订标识共同约束响应归属。

## 验收

覆盖快速连续输入、响应倒序、失败回滚、写入成功但响应丢失、双窗口同时保存和冲突后的草稿恢复。状态应对应当前草稿，冲突后用户输入仍可获取。

参考 [RFC 9110 · If-Match](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.1.1) 和 [乐观更新参考](render-and-state-diagnostics.md#参考用法)。
